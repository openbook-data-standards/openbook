# OpenBook ecosystem entry point

## Sources

Read the bundled [ecosystem catalog](references/ecosystem.md) for the bundle version, review date, public inventory and named readiness blockers. For newer information, read the [canonical catalog](https://github.com/openbook-data-standards/openbook/blob/main/docs/ecosystem.json) and [onboarding guide](https://github.com/openbook-data-standards/openbook/blob/main/docs/onboarding.md). Treat the bundled catalog as a dated observation, not current registry verification.

## Workflow

1. Determine whether the user wants to understand, publish, translate, consume, model exchange/routing/execution contracts, forecast, study racing or contribute. Ask one focused question if unclear.
2. Select only the relevant project and read its authoritative linked sources. Separate standards from runtime libraries and standalone experimental models. Do not install the entire family.
3. Route publishing to openbook-starter, translation to openbook-translate, consumption to openbook-js, exchange depth to OpenExchange, tokenized equivalence/quotes to OpenVenue, order lifecycle to OpenBook Betting, forecasting to OpenProb, racing orientation to OpenTrack. Specialist skills are optional; follow the public guide if they are not installed.
4. Check runtime, exact source revision, license, distribution and blocker status. Registry 404 for the JS packages is ONB-001; OpenTrack licensing is ONB-004; closed core/profile-envelope compatibility is ONB-005. Recheck evidence before changing those claims.
5. Offer the smallest synthetic first-success journey. Obtain consent before dependency installation, file writes or execution. Public orientation needs no provider account, database or cloud. Neon is an onboarding analogy, not a dependency.
6. If the user needs tooling, distinguish skills (instructions), authenticated tools/MCP (capabilities) and project initialization. Placeholder MCP/plugin discovery links do not establish a running server.

## Evidence

Report goal, chosen project, exact revision, source links, prerequisites, expected result, observed result and named blockers. An empty board or successful install is not proof of an integration. If no commands were authorized, describe a plan rather than claim runtime success.

## Boundaries

Follow the target repository's rules. Do not change schemas, enums, identity rules, licenses or compatibility without explicit authorization. Do not run tests locally; CI owns test execution. Never expose secrets, publish provider payloads, deploy, execute bets/payments or provision services as onboarding. Skills do not enforce permissions. Public source visibility is not a license, draft models are not interoperability guarantees, and source manifest versions are not evidence of published packages.
