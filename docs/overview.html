OpenBook — an open standard for sportsbook data

A clean-sheet standard for sportsbook & gambling data — the reference model, the live wire and the controlled vocabularies — independent of any sportsbook, data provider or software vendor. Existing industry feeds appear only as sources that map into it.

The short answer

There is no ISO standard for a sports or betting data feed. The nearest things are private or consortium specs — IPTC SportsML-G2, the Olympic Data Feed, and Sportradar's Unified Odds Feed — none of which is ISO. ISO only supplies the primitives everyone borrows: ISO 8601 time, ISO 4217 currency, ISO 3166 country, and ISO/IEC 27001 for the security wrapper.

So the field is open. This document defines what a good standard looks like — the model, object by object, the live wire, and the vocabularies.

The model

Seven principles carry the whole design.

  • Neutral, namespaced ids. The canonical id belongs to the standard, not to any provider. Every provider's id — a vendor URN, an integer, a slug — is mapped in; none of them is the master. This is the opposite of tying the model to one vendor's numbering.
  • Full names, no abbreviations. Objects are spelled out — reference_sport, reference_league, reference_market_type — because a standard is read by strangers.
  • Borrow ISO for the primitives. Time is ISO 8601, currency is ISO 4217, country is ISO 3166. Do not reinvent what already has a real standard.
  • Reference and live are different tiers. Reference objects (sport through fixture) are durable and bounded. Prices, scores and settlement are live streams and never sit in the reference tables.
  • Facts are derived, never copied from a source's presentation. Home vs away, the order of sides, the sign of a handicap — these are computed by the standard, not taken from whichever feed happened to arrive.
  • Mapping is part of the standard. Every source id resolves to a canonical id through a mapping record that carries a confidence and a review status. Reconciliation is a first-class feature, not an afterthought left to each integrator.
  • Live by default. Prices, scores and settlements are a stream, not a table you poll. Every change is pushed as a diff with a change signal — a doorbell — keyed by fixture and market. This is a live-data standard first: it should look like MQTT or a live transit feed, where the snapshot is just the stream caught up, not a REST endpoint you hammer.

The canonical id is a readable slug, not a number

Ids are namespaced and human-readable, in the spirit of a URN but legible on sight — you can tell what one points at without a lookup table:

  • sport:soccer, sport:basketball, sport:athletics
  • region:GB (ISO 3166), league:soccer:GB:premier-league, season:league:soccer:GB:premier-league:2025-26
  • segment:soccer:1st-half, segment:baseball:inning-1
  • market:total, market:player-points; a priced instance is market:total with a line, e.g. total=2.5
  • participant:soccer:GB:arsenal, player:<participant>:<slug>
  • fixture:<uuid> — minted by whichever schedule sees the match first (see object 9)

Every provider's own id — a vendor URN such as sr:match:, an integer, a slug — is carried on the mapping record, never used as the canonical key.

The name

The standard's working name is the OpenBook Data Standard — always written in full as a specification, never as a bare product name, to keep it clear of OpenBet, the sportsbook platform it would otherwise be confused with. It sits in the well-worn "open data standard" family: OpenRTB in ad-tech, OFX (Open Financial Exchange) and OCDS (Open Contracting Data Standard) in finance and procurement. The other naming family — formal ISO numbers like ISO 20022 (financial messaging) or ISO 8583 (card transactions) — is where this would land only if it were ever taken to a standards body.

Object naming. Inside the standard, objects are spelled out in full: reference_sport, reference_league, reference_market_type, with mapping tables to match (reference_map_sport, reference_map_market_type). Abbreviations save nobody any time and read badly to anyone outside the team that coined them.

1Sport

reference_sport — a canonical id, a display name, an abbreviation, and an active flag. The id is the standard's own; ISO has no sport list, so the vocabulary is the standard's to define and version.

Sources map in as:

  • Pinnacle / PS3838 — integer sportId in its own numbering (Soccer 29, Basketball 4, Baseball 3, Tennis 33).
  • OpticOdds — a string slug such as "soccer".
  • LSports — its own integer ids.
  • SportsML-G2 / Olympic Data Feed / Sportradar UOF — a vocabulary token / a three-letter code / a sr:sport: URN.

Design choice: a small, versioned sport vocabulary with a stable canonical id; every source is a mapping.

Better names for athletics & the Olympics

The Olympic Data Feed identifies athletics as ATH and its events as opaque codes — ATM012 is the men's 110m hurdles, sessions run ATH01–ATH25. You cannot read those without the codebook. OpenBook names them in the open, as a sport with readable disciplines beneath it:

  • sport:athletics — with disciplines athletics:100m, athletics:110m-hurdles, athletics:long-jump, athletics:marathon, athletics:decathlon, athletics:4x100m-relay.
  • The Olympics is a competition (a league/tournament), not a sport: league:athletics:INT:olympics, with a season per Games (...:2024-paris). A multi-sport Games is a set of these, one per sport.

The rule: a code should never need a lookup table to read. The mapping to ODF's ATH/ATM012 lives on the mapping record, so the terse source code is preserved without inflicting it on anyone.

2Region / Country / Location

reference_region (a country) keyed on its ISO 3166-1 alpha-2 code, with reference_location for sub-regions beneath it. The one object where a real ISO standard is the natural key.

Sources map in as:

  • Pinnacle / OpticOdds — no first-class country; it is buried in the league name ("England - Premier League") and must be split out.
  • Sportradar UOF — a category under a sport, often a country.

Design choice: ISO 3166 is the canonical key. A source that hides country in a name gets parsed on the way in.

3League / Competition / Season

reference_league — a canonical id with its sport, its region (a separate object, never text in the name), a name and abbreviation, and a clock/score/segment ruleset. reference_season hangs beneath it.

Sources map in as:

  • Pinnacle / PS3838 — league id, name, and a flag saying which side is home; country in the name.
  • OpticOdds — a league slug with the country embedded.
  • Sportradar UOF — a tournament → season → stage URN chain (the richest public model).

Design choice: country is a linked object, not a substring — the thing that otherwise breeds duplicate leagues. Adopt UOF's tournament/season/stage layering.

4Participant / Team

reference_participant — a team (or individual) with a canonical id, an alias set so a book's name matches with no second call, and an associations list for parent/child links. Home vs away is not a property of the participant — it is a role assigned on the fixture.

Sources map in as:

  • Pinnacle / PS3838 — Team1 and Team2, plus a flag for which is home; live odds use home/away, settlement uses team1/team2. Team1 is not always away.
  • Sportradar UOF — a competitor URN carrying an explicit home/away qualifier.
  • Provider ordering hints (rotation numbers, "flipped" flags, listed order) — describe that provider's presentation, not the fact; the standard ignores them.

Design choice: aliases are first-class, and side/order is a derived fact on the fixture. Trusting a feed's ordering is one of the most common real-world sources of mis-priced lines (a home/away swap on a single feed); the standard never does it.

5Player

reference_player — a player with a team, a position, and a canonical id. Bounded reference data, because a roster is bounded by league size.

Sources map in as:

  • Pinnacle / PS3838 — players appear only through props and specials (baseball pitchers), not a full roster.
  • OpticOdds — player rows; props arrive on the fixture-odds call.
  • Sportradar UOF — a player URN.

Design choice: roster is bounded reference data, not live state.

6Segment / Period hard

reference_segment — a canonical slice of a match (half, quarter, inning, set) with a normalised family that groups the vendor-specific numbering, defined per sport.

Sources map in as:

  • Pinnacle / PS3838 — a per-sport period number (416 rows across 62 sports). Zero is usually the full contest, but hockey zero means "OT included", baseball skips period 2, and tennis has 245 per-game rows.
  • OpticOdds — period implied by the market; baseball's "1st half" is the first five innings, so one market id means different segments in different sports.
  • Sportradar UOF — folded into the market specifier, not a first-class object.

Design choice: make the segment first-class and normalise vendor numbering into a family per sport — the only way to reconcile feeds that disagree slice by slice.

7Market type the centrepiece

reference_market_type — a canonical vocabulary of what can be bet: a genre, a shape (how the outcome is priced), a category (main lines, score props, game props, player props, outrights, parlay specials, same-game parlay), and prop flags. Main lines are moneyline, spread, total and team totals.

Sources map in as:

  • Pinnacle / PS3838 — a small fixed enum (spread, moneyline, total points, team total points, a couple of special shapes).
  • OpticOdds — free-string market names, one id reused across sports — so the mapping must be composite.
  • Sportradar UOF — a numeric market id plus a specifier, roughly a thousand markets; complete but proprietary.
  • SportsML / ODF — no betting-market concept at all.
This is where no cross-vendor taxonomy exists, so it is where the standard has the most to offer. A published market-type vocabulary is the real contribution — the piece literally no one else has.

Design choice: a versioned market vocabulary; source markets resolve through a composite mapping (market type, segment, side) keyed by sport.

8Side / Outcome

reference_side — a canonical outcome (home, away, over, under, draw). The sign of a handicap and the order of sides are derived by the standard, never taken from a source.

Sources map in as:

  • Pinnacle / PS3838 — team is TEAM1/TEAM2/DRAW, side is OVER/UNDER, handicap required for spread and total.
  • Sportradar UOF — an outcome whose id parses back to the competitor, plus an active flag.
  • SportsML — a result outcome, not a bet side.

Design choice: a canonical outcome set with side and sign computed, not copied.

9Fixture / Event the base object

reference_fixture — one match, the base object of the whole system, with a neutral fixture id any schedule can mint (deduplicated by sport, start instant and participant set). It carries name, start and cutoff instants, state, an in-play flag, its participants with their home/away roles, and a per-source binding object; prices and scores attach to it but live on the live tier.

Sources map in as:

  • Pinnacle / PS3838 — a fixture with an id and a parent id linking a live event to its pregame one, start, home/away, live status.
  • OpticOdds — an Optic fixture id; results resolve to the canonical fixture in the reader, never at write time.
  • Sportradar UOF — a match URN such as sr:match:8412480.

Design choice: a source-independent fixture id with an explicit dedup rule — so a fixture that only one minor source carries still gets a clean identity, which vendor-keyed models cannot give.

10Price / Odds

A price is live, not reference. Decimal odds are canonical; every price is a diff on one stream, keyed by fixture id and market key, and nothing else. Display formats (American, Hong Kong, and so on) are a presentation layer.

Sources map in as:

  • Pinnacle / PS3838 — an odds call with a line id, period status and maxes; a delta cursor returns only changed periods, so you merge, never replace.
  • OpticOdds — an odds call capped at five fixtures and five books, plus a props call.
  • Sportradar UOF — an odds-change message (markets → outcomes → odds) pushed over a queue — the closest public analogue.
  • SportsML / ODF — no odds concept.

Design choice: one push-and-diff stream, decimal canonical, keyed by fixture and market — the same shape UOF arrived at independently. Transport (queue, stream, socket) is interchangeable and not part of the standard.

11Score / State / Clock

A single live status object: match state, score, and clock, written by one producer in one shape with its own change signal.

Sources map in as:

  • Pinnacle / PS3838 — live soccer score on the odds call, clock on a separate in-running call.
  • OpticOdds — a results event over a streamed connection, carrying scores, in-play and stats.
  • Sportradar UOF — a sport-event-status block carried on the odds messages.
  • SportsML / ODF — their home turf; results, scores and phase stats are exactly what they standardise.

Design choice: one writer, one shape, one signal — score is not smuggled in on odds frames.

12Settlement / Grading / Result

A settlement per market and outcome (win, lose, void, half), with a companion rollback. A re-settle is a new settlement id, never a mutation of the old one.

Sources map in as:

  • Pinnacle / PS3838 — a settled call with per-period scores and a status; every re-settle mints a new id and timestamp. A 24-hour lookback, no backfill.
  • OpticOdds — a results call.
  • Sportradar UOF — a bet-settlement message plus a rollback message.
  • SportsML / ODF — final results and records, editorial rather than bet grades.

Design choice: immutable settlements with explicit rollback — Pinnacle's re-settle-as-new-id semantics, which are the cleanest around.

13IDs & mapping

reference_map_<kind> — a record per kind (sport, region, league, segment, side, participant, player) from a source id to a canonical id, carrying a confidence (exact, derived, name match) and a status (mapped, needs review, rejected). Market-type mapping is composite and keyed by sport. Rows that cannot be parsed go to a review queue.

Sources map in as:

  • Sportradar UOF — URNs throughout plus a market-mapping layer to a customer's ids — the only public spec that treats "map me to your ids" as first-class.
  • Everyone else — ships an id space and no mapping layer; reconciliation is left to the integrator.

Design choice: mapping, confidence and human review are part of the standard, not a private chore — this is what makes a neutral id space usable.

How the big books actually do it

The short version, after digging: the sportsbooks do not publish data standards at all. The books run proprietary catalogs; the providers they buy from are the real standardisers, and only one of them publishes a usable public taxonomy. This is the gap OpenBook is designed to fill.

The books — all proprietary, none public

  • DraftKings — runs the trading engine it acquired from SBTech in the 2020 merger (it dropped Kambi to bring trading in-house), and buys data from Sportradar and Genius Sports. No public developer API and no published market taxonomy; the market model is SBTech's internal catalog.
  • FanDuel — on Flutter's shared stack, whose differentiator is the "Flutter Edge" — proprietary pricing and risk-management ported across brands. It licenses content where it needs rights (IMG Arena for in-play golf, Sportradar/Genius for feeds) but publishes no taxonomy. correction the "Amelco runs FanDuel" idea is a common mix-up — Amelco's US source-code deal was with Fanatics, not FanDuel.
  • bet365 — the most in-house of the three: a proprietary platform built by Hillside Technology on Erlang and Elixir for real-time odds recalculation at huge concurrency, in its own datacentres. It takes third-party official-data feeds only where a rights mandate forces it. Nothing about its model is public.

The providers — where standardisation really happens

  • Sportradar (UOF) — the one genuinely usable public taxonomy. URN ids (sr:match:8412480), numeric market ids and outcome ids, and specifiers that collapse many markets into one — e.g. one "quarter handicap" market with a quarternr specifier covers all four quarters, and variable markets carry a variant URN. It ships a public market-descriptions catalog and a mapping layer back to its own legacy feeds — effectively Sportradar standardising Sportradar.
  • Genius Sports — an official sports-data API for pre-match, in-play and bet-builder markets; the market schema sits behind a partner login, so there is no public taxonomy to point at.
  • Stats Perform (Opta) — the F-series feeds (F24 timed events, F7 match) with stable canonical Opta ids for game/team/player. It is an events and stats model, not a betting-market model — books build markets on top of it.
  • IMG Arena — official-data rights packaged as "Event Centres" (golf, tennis, UFC); now being integrated into Sportradar, consolidating the rights layer further.

What "official data" standardises — and what it doesn't

Leagues force a single authoritative source: the NFL is Genius-exclusive (through 2030), the NBA went Sportradar-exclusive from 2023-24, and UK/EU soccer is Genius via Football DataCo through 2029. But a mandate standardises the source and the event definitions and timing — what counts as an event, and when — not a shared market schema. Each book still maps that feed into its own catalog.

The one openly documented bettable model: Betfair

The Betfair Exchange API is the only public, end-to-end selection model: EventType → Competition → Event → Market → Runner, where a bettable line is a selectionId plus a handicap. It is an exchange (runners, not bookmaker market templates), and it models periods as separate markets ("First Half Goals") rather than with a specifier — the opposite of Sportradar's approach.

The takeaway. There are only two ways the industry standardises anything today: official-data mandates (feed-level, source + event timing) and vendor-internal mapping layers (Sportradar to its own legacy feeds). No neutral, cross-vendor market taxonomy exists — every book privately re-maps a provider feed into its own catalog. That absence is exactly the space a published market-type vocabulary fills.

Where OpenBook sits: on periods it takes the middle path — a first-class segment object, rather than Betfair's "a market per half" or Sportradar's "a specifier inside the market". On selections it follows the clearest public model (Betfair's outcome + handicap). On the market vocabulary it does the thing no one has published.

Where the work is

Easy. Country, sport and player. ISO 3166 gives country outright; sport is a short vocabulary; a roster is bounded. These fall out almost for free.

Medium. League, participant/side and fixture. Keep country a separate object, derive side order rather than trust a feed, and give fixtures a neutral id with a real dedup rule.

Hard, and the point. Market type, segment/period and the odds wire. No cross-vendor taxonomy exists, period numbering disagrees per sport, and odds transport is per-vendor. This is exactly where a standard earns its keep — and the market-type vocabulary is the piece nobody else has.

Scope & governance

OpenBook standardises the data contract — the schemas and the controlled vocabularies — and nothing else. How any sportsbook, data provider or vendor produces, models or prices the data behind a conformant feed is out of scope and entirely their own. The specification is published under an open licence (CC BY 4.0); a validator and conformance suite make "OpenBook-conformant" a testable claim.

Governance is staged the way live-data standards actually reached adoption: published openly under one steward first, with adoption driven by the quality of the vocabulary and tooling (the GTFS and OpenTelemetry route); a lightweight working group only once several non-competing adopters exist; a formal standards body only if the ecosystem asks for it. An ISO number is an outcome, not a starting move.

Cross-industry analogues

Every one of these opened a data standard while the implementations stayed private and competitive. Closest first.

Live public-transit feeds — the closest structural match live-data model

Public transit already solved this exact shape, in the open. GTFS is the static reference layer — agencies, routes, stops, trips — and GTFS-Realtime and SIRI are the live layer on top: trip updates, vehicle positions and arrival predictions, delivered as changes against those stable ids. The parallel is almost one-to-one:

  • Their reference tier (routes, stops, trips) is OpenBook's reference tier (sport, league, fixture).
  • Their live tier (a vehicle moving, an arrival re-predicted) is OpenBook's live tier (odds moving, a score changing, a bet settling).
  • The live feed carries only what changed and points back at stable reference ids — never re-sending the timetable. That is exactly the fixture-plus-market-key diff rule.

Open schema, public feed, private systems behind it: every agency runs its own back office, but they all publish GTFS. That is the model OpenBook's live side follows.

OpenRTB — ad-tech real-time bidding market structure

The IAB publishes the bid request/response and the category taxonomies openly; every platform implements them privately and competes on its models. Real-time auctions, latency-critical, fierce competition, and the taxonomy is the product — yet the schema is fully open. The market structure closest to gambling.

FIX Protocol — electronic trading

An open message spec governed by a non-profit; banks and high-frequency shops all speak it while their execution algos stay secret. Proof it works with money on the line, zero trust and low latency.

OpenTelemetry — observability

An open data model, protocol and reference SDKs; vendors keep their backends proprietary. It became the standard in about four years with no mandate, purely because the open schema and reference implementation were too good to fight. The gravity path.

FHIR — and how GTFS got started

FHIR is an open health-data standard with private record systems behind it. And GTFS — the transit model above — is proof a single publisher can seed a world standard: it began as one agency and Google publishing a schema and a sample feed, and adoption did the rest. That is the position any first publisher of OpenBook would be in.

The common shape: an open schema and vocabulary, usually a reference implementation, and private data production. None needed an ISO number to win.

The ISO question

No ISO standard defines a sports or betting data feed — confirmed against ISO's own catalogue and the vendor landscape as of September 2026.

ISO appears only as primitives: ISO 8601 for time, ISO 4217 for currency, ISO 3166 for country, and ISO/IEC 27001 as the security and compliance wrapper, which says nothing about the shape of the data. One curiosity: OData 4.0 is ISO/IEC 20802, a generic REST convention, but it is not sports-specific.

The ISO standards everyone names are management systems — ISO 9001 (quality), 14001 (environment), 45001 (safety), 27001 (security), 22000 (food). None of them is a data feed, and this is not one of them. The relevant lineage is live data, where the good models are mostly outside ISO: the open public-transit feeds (GTFS-Realtime, SIRI) and, on the ISO side, ISO/IEC 20922 — MQTT, the real-time pub/sub protocol. That is the family OpenBook belongs to, not the management-system one.

The de-facto standards are consortium or vendor specs: IPTC's SportsML-G2 and Sport Schema (results and editorial, no odds); the Olympic Data Feed (results); Sportradar's Unified Odds Feed (URN ids, odds-change and settlement messages, a market-plus-specifier taxonomy and a mapping layer — proprietary); and the trading feeds from Genius and OpenBet (also proprietary).
